# テスト、リリース、アーキテクチャの進化計画

このファイルは、現在のローカル `dry_run` から Bybit への `bybit-automation` を定義します。
デモ、リリース候補 (RC)、限定的な Live Canary 検証プロセス。未来も記録する
マイクロサービス/分散アーキテクチャに進化するかどうか、またどのように進化するか。

このドキュメントは実行計画であり、すべてのコマンドや機能が実装されていることを意味するものではありません。各段階には、現在のステータスが明確にマークされています。

## 1. 核心的な結論

- 現在の位置付け: モジュール式モノリスのデモ検証の初期段階。
- 適切になりました: まず、単一の手順のトランザクション セキュリティとデモ検証を完了します。
- 中期的に適しています: すぐに多数のマイクロサービスに分割するのではなく、必要に応じていくつかの粗いサービスに分割します。
- Live の前に、このファイルの Gate 0 から Gate 6 を順番に通過する必要があります。
- ポジションを作成、キャンセル、またはクローズするすべての操作は、唯一の `OrderManager`/トランザクション ライターによってのみ実行できます。
- Bybit は外部トランザクションの信頼できる情報源です。 SQLite/将来の PostgreSQL はネイティブの永続レコードです。レディス
  再構築可能なキャッシュおよび調整レイヤーとしてのみ使用できます。

## 2. ステータスインジケーター

- **すでに利用可能**: プログラムには現在、対応する入学テストまたは自動テストがあります。
- **部分的に利用可能**: 基礎となるコンポーネントは利用可能ですが、実際の統合検証はまだ完了していません。
- **実装予定**: 正式実装前に追加する必要があります。
- **手動承認**: デモまたはライブ トランザクションの副作用が発生するため、一般的な自動テストでは直接実行できません。

## 3. 現在存在する検証入口

|目的 |コマンド |ステータス |重要な制限事項 |
| --- | --- | --- | --- |
|オフラインテスト | `uv run pytest` |すでに入手可能 |フェイク/モックを使用しても Bybit に接続できるわけではありません。
|静的チェック | `uv run ruff check .` |すでに入手可能 |実行時または交換動作は検証しません。
|単一の実行時ティック | `uv run bybit-automation test --config <path>` |すでに入手可能 | config が `demo`/`live` の場合、注文は実際に送信される可能性があります。
|強制ドライラン検証 | `uv run bybit-automation verify-dry-run --config <path>` |すでに入手可能 | Bybit には接続せず、ローカル プロセスのみを確認します。
|設定変更確認 | `uv run bybit-automation reload --current <path> --candidate <path>` |一部利用可能 |別の実行中のプログラムを直接更新しません。
|長いランタイム | `uv run bybit-automation run --config <path>` |すでに入手可能 |これは正式な実行エントリですが、運用準備が完了したことを意味するものではありません。
|デモ読み取り専用プリフライト |まだコマンドがありません |実装予定 |トランザクションの副作用がゼロであることを保証する必要があります。
|デモシャドウモード |まだコマンドがありません/独立した実行ゲート |実装予定 |現在、`demo` によりデモ注文の実行が有効になります。

## 4. グローバル トランザクション セキュリティ ルール

デモまたはライブのネットワーク検証は次の条件に準拠する必要があります。

1. 独立した API キーを使用します。ライブキーの出金許可をオフにする必要があります。
2. API シークレットは、環境変数またはローカル シークレット ストアを通じてのみ提供でき、Git に書き込むことはできません。
3. テスト前に環境、口座、シンボル、最大金額、最大許容損失、停止条件を明確に記録します。
4. ポジションは手動の承認なしに確立、キャンセル、変更、またはクローズすることはできません。
5. `test` コマンドは、構成が `dry_run` であることが確認された場合にのみ、副作用のないコマンドと見なされます。
6. デモ/ライブは、「接続できる」ことと「注文を送信できる」ことを区別する必要があります。 `app.mode` を使用して 2 つのものを同時に制御することはできません。
7. ポジション決済注文では、`reduceOnly`、ポジション モード、`positionIdx`、および実際の取引方向を検証する必要があります。
8. すべての注文には安定したクライアント注文 ID/冪等性キーがあり、「取引所によって受け入れられた」を処理できなければなりません。
   しかし、マシンは応答を受け取りませんでした。」
9. 自動テストでは、ローカル ロボットによって作成されたことが確認できないアカウントの注文をキャンセルすることはできません。
10. ステータスを判断できない場合は、新規エントリを中止し、`SAFE_MODE` を入力します。

## 5. 段階的なテストとリリースゲート

### ゲート 0: 開発環境とオフライン ベースラインステータス: ** テストが利用可能です。マシンはまだ再実行されていません。 **

目的: 現在のコミットをクリーンな環境から再構築できること、および外部サービスを必要としないすべてのテストに合格することを確認します。

実行:

```powershell
uv sync --locked
uv run python --version
uv run pytest
uv run ruff check .
```

最低受け入れ条件:

- `uv sync --locked` 成功しました。
・Pythonのバージョンは`pyproject.toml`に準拠します。
- すべてのテストとラフに合格しました。
- テストプロセスには Bybit 認証情報は必要ありません。
- Git ワークツリーには予期しないアーティファクトやシークレットはありません。

保存すべき証拠:

- コミットハッシュ、実行時間、OS、Python/UV バージョン。
- pytest と Ruff の結果。
- 失敗したテストと修復の記録。

### ゲート 1: ドライラン実行時間検証

ステータス: ** すでに利用可能です。 **

目的: Bybit に触れることなく、完全なランタイム アセンブリ、SQLite の記述、ポリシー/リスク制御の決定、安全なシャットダウンを検証します。

実行:

```powershell
uv run bybit-automation verify-dry-run --config configs/config.template.toml
uv run bybit-automation test --config configs/config.template.toml
```

以下もテストする必要があります:

- `verify-dry-run` `demo` および `live` 構成は拒否する必要があります。
- 構成が欠落している、無効なシンボル、負の間隔、または間違ったデータベース パスがある場合のエラーをクリアします。
- SQLite WAL、スキーマ ブートストラップ、構成バージョン、および `bot_state` は正常です。
- 2 回続けて起動すると、新しい位置が古い後続状態を継承できなくなります。
- `Ctrl+C`／SIGTERM はシャットダウン理由を保存します。
- ccxt Bybit クライアントはドライランでは作成されず、ポジションの作成、キャンセル、クローズも行われません。

最小限の受け入れ条件: すべての検査に合格し、「ゼロ Bybit ネットワーク リクエスト」の証拠を提供できます。

### ゲート 2: Bybit デモの読み取り専用プリフライト

ステータス: **実装予定。 **

新しい入り口の提案:

```powershell
uv run bybit-automation preflight --config configs/config.demo.toml
```

目的: 資格情報、ネットワーク、アカウント モード、マーケット設定を確認しますが、Bybit ステータスはまったく変更されません。

プリフライトでは以下のみが許可されます。

- サーバー時刻と時刻偏差をクエリします。
- アカウント/API 権限を照会し、デモ環境であることを確認します。
- 設定されたシンボルと市場メタデータを読み取ります。
- ティッカー、OHLCV、オープンポジション、未約定注文を読み取ります。
- 最小注文数量、価格ティック、数量精度、位置モードを読み取ります。
- ヘルスレポートと SQLite 監査レコードを作成します。

プリフライトでは特に次のことが禁止されています。

- レバレッジを設定します。
- 注文を作成、変更、またはキャンセルします。
- ポジションを決済します。
- アカウント設定を変更します。

最低受け入れ条件:- 現在の接続がライブではなくデモであることをプログラムで証明できます。
- 設定されたすべてのシンボルを解析できます。
- 権限とアカウントのパターンは期待どおりです。
- 約定前後のポジションはオープン注文とまったく同じです。
- いずれかのチェックが失敗した場合、トランザクションの副作用はなく、ゼロ以外の終了コードが返されます。

### ゲート 3: デモ シャドウ モード

ステータス: **実装予定。 **

目的: 実際のデモ相場とアカウント情報を使用して完全な戦略を実行しますが、すべての取引所の副作用をブロックします。

実装の前提条件: 接続環境と実行権限を分離します。次に例を示します。

```toml
[app]
mode = "demo"

[execution]
enabled = false
```

「金額を0に設定」は、将来の注文のキャンセル、ポジションの決済、または新規追加を保証するものではないため、約定ゲートの代わりに使用することはできません。
副作用はブロックされます。

テスト内容:

- デモティッカー、Kライン、ポジション、オープンオーダーを読みます。
- 実行戦略、リスク管理、スケジューリング、および持続性。
- SQLite に注文インテントを書き込みますが、`submitted=false`。
- 位置の不一致、WebSocket の失効、Redis の利用不可、API タイムアウトをシミュレートします。
- `SAFE_MODE` は新しいエントリを停止しますが、監査可能なリスク制御の決定を生成することを確認しました。
- 少なくとも 30 分間実行し、その後 2 時間および 24 時間のシャドウ セッションを実行します。

最小承認条件: Bybit デモ アカウントには、セッション全体の前後でシステムによってステータスが変化しないこと。

### ゲート 4: 制御されたデモ注文のライフ サイクル

ステータス: **実装予定。各テストには手動による承認が必要です。 **

前提条件: ゲート 0 からゲート 3 まですべてパスし、単一の高流動性シンボルと取引に許可される最小金額を使用します。

順番に実行され、一度に自動的に完了することはできません。

1. すぐには実行されない少額の指値注文を作成します。
2. REST から注文をクエリし、クライアント注文 ID を使用して SQLite インテントと一致します。
3. ロボットによって作成された注文をキャンセルし、他の注文に影響を与えないことを確認します。
4. 取引可能な少額のデモ注文を作成し、注文・約定・ポジション状況を確認します。
5. `reduceOnly` を使用してポジションを決済し、逆ポジションが開かれないことを確認します。
6. 注文結果を繰り返し取得し、イベントの再送信によって重複したローカル レコードが作成されないことを確認します。
7. 正常なシャットダウンをテストして、ローカル ロボットに属する未処理の注文のみを処理します。

例外ケース:

- 注文送信後の応答タイムアウトを意図的にシミュレートし、クライアントの注文 ID を使用して交換結果を確認します。
- 冪等の保護を確認するために、同じインテントを繰り返し送信します。
- 注文が一部満たされた後はキャンセルされます。
- ポジションを決済するとマーク価格が急速に変化します。
- 位置モードが設定と一致しません。最小受諾条件: 重複注文なし、ポジションの逆オープンなし、誤って手動注文キャンセルなし、SQLite は完全に再構築可能
各インテントと交換注文/実行の関係。

### ゲート 5: 調整と障害回復訓練

ステータス: **部分的に利用可能。基本コンポーネントは利用可能ですが、完全な統合を完了する必要があります。 **

テストが必要な状況:

|失敗 |期待される動作 |
| --- | --- |
|起動時、Bybit の位置は不明です | `SAFE_MODE` と入力し、新しいエントリを停止します。
| Bybit には起動時にローカルの不明な注文があります。 `SAFE_MODE` と入力すると、直接キャンセルできません |
| SQLite が注文を送信しましたが、Bybit が注文を見つけることができません。レコードの不一致、手動確認またはセキュリティ修復 |
|注文配達後のインターネットタイムアウト |最初に注文を確認/調整し、やみくもに再送しないでください。
| WebSocket の中断またはデータの有効期限切れ |新しいエントリを一時停止し、REST 修復後に再開します。
| Redis の中断/再起動 |実行時の安全性のダウングレード。 Exchange および耐久性ストアからキャッシュを再構築する |
| SQLiteがロック／書き込み不可／ディスク不足 |トランザクションの副作用の追加を停止し、エラーを発行／SAFE_MODE |
|ランタイムが強制終了された後に再起動される |調整が正常に開始されるまでは、エントリは許可されません。
|重複したイベント、順序が正しくないイベント、または遅延したイベント |イベント ID/シーケンスに基づく重複排除、ステータスの逆転なし |
|継続的な API エラー |バックオフとサーキットブレーカーが実際に有効になる |
|無効な設定のリロード |古い設定を保持し、監査記録を残す |

完了する必要があります:

- 起動時に調整するだけではなく、`reconciliation_interval_sec` をスケジューラに接続します。
- 再試行/バックオフ/サーキット ブレーカーを読み取り操作に統合し、再試行を明示的に許可します。
- SAFE_MODEの回復条件とマニュアル操作マニュアルを定義します。
- 各交換の副作用に冪等性とあいまいな結果の処理を追加します。
- メモリ内の通知リストだけでなく、外部通知を追加します。

最小許容条件: すべての失敗は「安全な停止または安全なダウングレード」であり、説明できないトランザクションの副作用はありません。

### ゲート 6: デモ ソーク テストとリリース候補

ステータス: **実行保留中。 **

推奨時刻表：

1. 2時間のシャドウ。
2. 24時間影。
3. 24時間限定のデモ取引。
4. 72 時間のデモソーク。

期間監視:- API/WebSocket の遅延、エラー率、再接続時間。
- 鮮度を引用します。
- 戦略/リスクのチェックは予定通りに行われていますか?
- オープン注文、ポジション、SQLite の不一致時間。
- SAFE_MODE の回数、理由、および回復時間。
- 繰り返されるインテント/順序/実行の数。
- SQLite のサイズ、書き込みレイテンシー、および WAL の動作。
- Redis の可用性とキャッシュの再構築時間。
- 通知が許容可能な時間内に配信されたかどうか。
- CPU、メモリ、ファイル記述子、および長期的なリソースの増加。

RC の最小許容条件:

- 72 時間以内に、原因不明のクラッシュ、重複注文、または間違ったポジションは発生しません。
- 意図的に再起動するたびに、調整して正しい状態を復元できます。
- すべての不一致は自動的に安全に処理されるか、SAFE_MODE に入ることができます。
- オペレータはファイルとアラームからシステムが現在安全であるかどうかを判断できます。
- デプロイメント、ロールバック、バックアップ、復元、キルスイッチの訓練。

### ゲート 7: 生きたカナリア

ステータス: **まだ許可されていません。 **

Live Canary は、ゲート 0 からゲート 6 がすべて通過し、ユーザーによって再度明示的に承認された場合にのみ計画できます。

最低限の保護:

- 出金許可のない独立したライブ API キー。
- 単一アカウント、単一シンボル、許容可能な最小ポジション。
- 1 日の最大損失、最大ポジション表記、および最大オープン注文を設定します。
- すぐに使用できるグローバル キル スイッチ。
- 起動時に明示的なライブ警告を表示し、二次確認または展開レベルの承認を要求します。
- 外部通知、ヘルスモニター、手動による出席。
- 最初に `reduceOnly` で決済ポジションを確認し、その後新しいポジションの確立を許可します。

ライブ カナリアは、通常の CI によって自動的にトリガーされるべきではありません。

## 7. マイクロサービスと分散アーキテクチャの違い

この 2 つは相互に排他的なオプションではありません。

- **分散アーキテクチャ**: 異なるプログラムまたはマシン上のコンポーネントのコラボレーションは、より大きな概念です。
- **マイクロサービス**: 機能を独立してデプロイ、拡張、保守できる小さなサービスに分割する分散型アーキテクチャの一種。
- **モジュラー ユニット**: 導入ユニットですが、プログラム内では明確なモジュールとインターフェイスが維持されます。マイクロサービスは、独立した展開および拡張機能をもたらしますが、ネットワーク障害、メッセージの重複/無秩序化、サービス間の調整、
分散トレース、バージョン互換性、およびメンテナンスコストの増加。取引システムの場合、これらは単にエンジニアリングの複雑さだけではありません。
誤った取引のリスクが直接的に高まります。

## 8. 現在のプロジェクトに最も適しているのはどれですか?

|オプション |現在のフィットネス |理由 |
| --- | --- | --- |
|モジュラーモノリス |最適な用途 |単一のアカウント、低から中程度のトランザクション量、単一のトランザクション ライターにより監査と調整が容易 |
|少数の粗粒な分散サービス |中期的に最適 |市場、トランザクションコア、および操作インターフェイスには明確な境界があり、個別に拡張できます。
|多数のきめ細かいマイクロサービス |今は適切ではありません |メンテナンスと整合性のコストが高く、既存のセキュリティ検証が完了していない |

現時点で最も価値のある投資は、デモの検証、冪等の発注、定期的な調整、外部アラーム、および障害訓練を完了することです。
これらの機能が完了する前にマイクロサービスを解体しても、未解決の状態一貫性の問題がネットワークに移されるだけです。

## 9. 提案された進歩的なアーキテクチャ

### フェーズ A: モジュール式モノリスの維持

単一プロセスを維持しながら内部境界を強化します。

```text
Market Data
    -> Strategy / Risk
    -> Order Intent
    -> OrderManager（唯一交易寫入者）
    -> Exchange
    -> Persistence / Notification
```

このフェーズではゲート 0 からゲート 6 が完了し、最初にそれらを内部で構築します。

- コマンド/イベント モデルを明確にする。
- クライアントのオーダー ID と冪等性。
- トランザクション/送信ボックスの境界。
- 定期的な調整。
- 可観測性、アラート、キルスイッチ。

### フェーズ B: 3 つの大まかなサービスに分割

独立した拡張または展開が必要な場合にのみ逆アセンブルしてください。

1. **市場データ ゲートウェイ**
   - Bybit パブリック WebSocket／REST マーケット スナップショットを維持します。
   - ティッカー、クライン、鮮度イベントを投稿します。
   ・個人取引の許可を有していない場合は注文することができません。

2. **トレーディングコア**
   - 戦略、リスク、ポジション状態、調整、および `OrderManager` を保持します。
   - ポジションをオープン、キャンセル、クローズできる各口座の唯一のサービスです。
   - セキュリティが成熟する前に、リスクと実行をネットワークの両端に分割しないでください。

3. **操作/コントロール プレーン**
   - ヘルス、構成提案、承認、通知、監査クエリ、キルスイッチを提供します。
   - Trading Coreをバイパスして取引所を直接呼び出すことはできません。

データ層の提案:- マルチプログラム/マルチマシンの後、SQLite ファイルは共有されません。代わりに、安全に並列化できる PostgreSQL などの耐久性のあるストアが使用されます。
- Redis は、唯一のトランザクション レコードとしてではなく、キャッシュ、ロック、または短期調整を維持します。
- イベント配信の場合、最初に Redis Streams、NATS JetStream、または RabbitMQ から 1 つを選択できます。要件が明確になる前に
  Kafka を直接インポートする必要はありません。

### ステージ C: 明確なニーズがある場合にのみマイクロサービスを追加する

次の状況が発生した場合にのみ、戦略ワーカー、実行サービス、およびリコンシリエーションの削除を検討してください。
サービスおよびその他のより詳細なサービス:

- 複数のアカウントまたは取引所を同時に管理します。
- 複数の戦略を個別に展開し、スケーリングする必要があります。
- 市場のスループットは、単一のプログラムの能力よりもはるかに高くなります。
- さまざまなチームには独立したリリース サイクルが必要です。
- 単一のプログラムが、測定可能なパフォーマンスまたは可用性のボトルネックになっています。

独立した実行サービスを削除した後も、次のことを確認する必要があります。

- アカウントごとに有効なトランザクション書き込み者は常に 1 人だけです。
- メッセージが少なくとも 1 回の場合、コンシューマは冪等である必要があります。
- コマンドは安定した冪等性キーを使用します。
- 送信ボックス/受信ボックス、または同等のメカニズムを使用して、データは送信されても​​イベントが失われることを回避します。
- ソート/パーティションの基準としてアカウント + シンボルを使用します。
- リーダーの選出は、古いリーダーが注文を継続できないようにフェンシング トークンと協力する必要があります。
- 調整により、交換ステータスの失われたイベントまたは順序が狂ったイベントを常に修正できます。

## 10. アーキテクチャのアップグレードの決定しきい値

「サービスを廃止する必要がありますか?」と答える前に、まず以下を収集してください。

- 単一ランタイムの CPU、メモリ、および API レイテンシー。
- シンボル、アカウント、戦略の数の増加が予想されます。
- 許容可能なダウンタイムと回復時間。
- 各モジュールを個別にデプロイする必要があるかどうか。
- ブローカー、PostgreSQL、可観測性、およびマルチサービス展開を維持するための人的資源があるかどうか。

まだ 1 人のユーザー、1 つの Bybit アカウント、少数のシンボルがある場合は、モジュール化しておくことをお勧めします。市場のとき
データを個別に拡張する必要がある場合、または複数のポリシー/アカウントを分離する必要がある場合は、ステージ B に入ります。これは、直接の包括的なマイクロサービスよりも優れています。
トランザクションステータスの問題をより安全に特定しやすくなります。

## 11. 次のステップの推奨順序1. `uv` 環境を復元し、ゲート 0 を実行します。
2. ゲート 1 を再実行し、現在のコミットの検証証拠を保存します。
3. 読み取り専用のデモ プリフライトを実装します。
4. Exchange環境を実行権限から分離し、シャドウモードを追加します。
5. クライアントの注文 ID、`reduceOnly`、定期的な調整、および外部通知を入力します。
6. 制御されたデモ注文のライフサイクル、障害ドリル、ソーク テストを実行します。
7. ゲート 6 を通過した後、フェーズ B でサービス分割を続行するかどうかが決定されます。
