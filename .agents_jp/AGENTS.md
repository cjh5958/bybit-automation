# エージェント.md

このドキュメントは、AI エージェントと開発者向けの実用的な引継ぎ書です。
このリポジトリのリファクタリング。

## プロジェクトの概要

このリポジトリには現在、次のように分割された小さな Bybit 先物取引ボットが含まれています。
2 つの独立した Python スクリプト:

- `strategy_bybit.py`
- `trail_bybit.py`

ヘルパー セットアップ スクリプトもあります。

- `fast_setup.py`

現在のレガシー スクリプトは個人用/実験用として書かれているようです。
`ccxt`、`pandas`、およびスクリプトローカル通知を使用した自動取引システム。

ユーザーの目標は、これを徐々にリファクタリングして、より信頼性の高い単一プロセスにすることです。
取引サービス:

- Python 環境および依存関係管理用の `uv`。
- SQLite による永続的な状態、イベント履歴、リカバリ。
- リアルタイム キャッシュ、調整、および短期間の状態のための Redis。
- WebSocket ベースの同期が役立つ場合。
- より安全な実行時の動作、状態回復、調整、構成のリロード。

ユーザーはすでに `dev` ブランチを作成しており、作業を続行したいと考えています。
検証可能な小さなフェーズ。

## 現在のスクリプトの動作

### `strategy_bybit.py`

このスクリプトはエントリー・注文戦略ボットです。

観察された動作:- `./configs` から設定ファイルをロードします。
  - `exchange_config.json`
  - `strategy_config.json`
  - `trailing_config.json`
- `ccxt.bybit` を通じて Bybit に接続します。
- オプションで Bybit デモ取引を有効にします。
- 構成された取引ペアのレバレッジを設定します。
- 構成から `trading_pairs` を読み取ります。
- `monitor_interval` でポーリング ループを実行します。
- 各ペアについて:
  - 現在のティッカー価格を取得します。
  - OHLCV キャンドルを取得します。
  - EMA トレンドを計算します。
  - ATR を計算します。
  - 平均振幅を計算します。
  - ボラティリティから導出された距離を使用して指値エントリー注文を発注します。
    - 強気トレンドの場合は、現在の価格よりも低い買い指値を設定します。
    - 弱気トレンドの場合は、現在の価格よりも高い売り指値を設定します。
  - 新しい注文を行う前に、ペアのオープン注文をキャンセルします。
- レバレッジ、手数料、設定を使用して設定されたUSDT金額を契約金額に変換します。
  そして最低額を両替します。

推定される開発者の意図:

- ボラティリティが調整された価格付近で指値エントリー注文を自動的に維持します。
- EMA をトレンド フィルターとして使用します。
- ATR と平均振幅を使用して次数距離を選択します。
- 構成されたシンボルごとに長期および短期の両方の機会を管理します。

### `trail_bybit.py`

このスクリプトはポジションリスク/トレーリングボットです。

観察された動作:- 同じ設定ファイルを `./configs` からロードします。
- `ccxt.bybit` を通じて Bybit に接続します。
- 構成資格情報を使用して、従来のスクリプトローカル通知コードを初期化します。
- `monitor_interval` で頻繁なポーリング ループを実行します。
- すべての位置を取得します。
- ゼロ以外の各位置について:
  - `blacklist` のシンボルをスキップします。
  - 新しい位置を検出し、レガシー通知を送信します。
  - 現在の利益率を計算します。
  - メモリ内の最高利益率を追跡します。
  - しきい値に基づいて後続層を割り当てます。
    - `low_trail_enable_threshold`
    - `first_trail_enable_threshold`
    - `second_trail_enable_threshold`
  - 適用:
    - 固定ストップロス、
    - 低層トレーリングストップ、
    - 第一層トレーリングストップ、
    - 2 段目のトレーリング ストップ。
  - 成行注文を使用してポジションをクローズします。
  - 検出/クローズされたポジションに関してレガシーメッセージを送信します。

推定される開発者の意図:

- 別のプロセス/スクリプトに、すでにオープンしているポジションを管理させます。
- ストップロスと多段階のトレーリングテイクプロフィットでポジションを保護します。
- ポジションが検出またはクローズされたときにユーザーに通知します。

## 現在のアーキテクチャの問題主な問題はコードのスタイルだけではありません。ランタイム モデルは次の理由により危険です。
独立したプロセスは、状態を共有せずに同じ取引口座で動作します。

既知または推測される問題:- `strategy_bybit.py` と `trail_bybit.py` は両方とも Exchange クライアントを初期化し、
  独立して実行します。
- ストラテジーは、トレーリング/リスクスクリプトが実行されている間に注文をキャンセルして再作成できます。
  共有ステートマシンを使用せずにポジションを管理します。
- 中央の `OrderManager` はありません。
- 以下については永続的な状態がありません。
  - 最高の利益、
  - アクティブな後続層、
  - 最後に知られている位置の状態、
  - 注文のライフサイクル、
  - 戦略の決定。
- `highest_profits`、`current_tiers`、および検出された位置はメモリ内にのみ保存されます。
  これらは再起動すると失われます。
- 設定は起動時にのみロードされます。
- 設定ファイルは `ChainMap` とマージされます。重複キーなど
  `monitor_interval` は曖昧であり、相互に影を落とす可能性があります。
・ ロガーのセットアップが重複している。
- どちらのスクリプトにも、mojibake/エンコーディングが破損した繁体字中国語のログが含まれています
  文字列。一部の文字列は構文的に安全でない可能性があるため、毎回チェックする必要があります。
  動作する Python ランタイムが利用可能です。
- REST ポーリングは市場/アカウントの状態に使用されますが、速度が遅く、レートが制限されています。
  また、WebSocket ストリームよりもネットワーク ドリフトに対して脆弱です。
- 明示的なセーフ モード、調整、サーキット ブレーカー、または再起動回復はありません。- 現在のエラー処理には、次のような修正が必要なパターンが含まれています。
  再帰的再試行パスとネットワーク状態の処理が弱い。

## ターゲット製品の意図

将来予定されているシステムは、単一の取引サービスのように動作する必要があります。

```text
market/account sync
  -> strategy decision
  -> order intent
  -> order execution
  -> position tracking
  -> risk/trailing decision
  -> durable event/state storage
  -> notification
```

サービスには 1 つのプロセス、1 つの調整されたランタイム状態、および 1 つのパスが必要です
すべての交換の副作用に対応します。

重要な設計原則:

> すべての取引所の副作用、特に注文の発注、注文のキャンセル、
> ポジションをクローズするには、集中型の `OrderManager` を経由する必要があります。

これにより、戦略とリスク ロジックの間で操作が競合するのを防ぎます。

## ティックの定義

以前の議論で、「ティック」が次のことを意味することを明らかにしました。

- プログラム決定ティック: ボットの決定パイプラインの 1 つのパス。

次のような意味であってはなりません:

- すべての交換マッチングエンジンのチェック。既存の戦略は、すべての為替取引ティックを処理するのには適していません。
現在のスクリプトは、より遅いリズムを暗示しています。

- 戦略ループ: およそ分レベルのポーリング。
- トレーリング ループ: およそ第 2 レベルのポーリング。

将来の設計では以下を分離する必要があります。

- WebSocket/イベント取り込みの頻度。
- 意思決定ループのリズム。
- 戦略評価の頻度。
- リスク/トレーリング評価の頻度。
- REST 調整の頻度。

ターゲット SLA の例:

```text
Market data freshness target: under 500ms when WebSocket is healthy.
Risk decision cadence: 250ms to 1s, configurable.
Strategy decision cadence: 30s to 60s, configurable.
REST reconciliation cadence: 10s to 30s, configurable.
```

すべての為替取引ティックを処理することを約束しないでください。代わりに、リズムを作りましょう
期限を明示し、強制します。

## SQLite と Redis の責任

### SQLite

SQLite は、状態と履歴の永続的なソースです。

SQLite は次の目的で使用します。

- 注文
- イベントの注文
- 取引/約定
- スナップショットの位置
- 戦略の決定
- リスクイベント
- ボットの状態
- 構成バージョン
- 通知ログ

推奨される SQLite の動作:

- WAL モードを有効にします。
- 複数ステップの状態更新にはトランザクションを使用します。
- 重要な取引イベントについては、追加専用のイベント レコードを優先します。
- プロセスの再起動後に回復できるように十分なデータを保存します。

### レディス

Redis はリアルタイムのキャッシュおよび調整レイヤーであり、永続的なソースではありません。
真実。

Redis を次の目的で使用します。- 最新のティッカー/マーク価格
- 最近の K ライン バッファ
- アクティブな位置のキャッシュ
- オープン注文キャッシュ
- シンボルごとのロック
- 軽量のパブ/サブイベント
- 設定リロード信号

Redis が再起動した場合、ボットは SQLite と
交換。

## データの安全性と回復

将来のサービスはシャットダウン、ネットワーク障害、再起動を処理する必要があります。
古い仮定に基づいて盲目的に取引することはありません。

必要な動作:

- 起動時に、ストラテジー取引の前に調整を実行します。
  - 取引所からオープン注文を取得し、
  - 取引所からアクティブなポジションを取得し、
  - 必要に応じて残高を取得します。
  - 交換状態を SQLite の最新の既知の状態と比較します。
- 状態が矛盾している場合は、`SAFE_MODE` を入力します。
- `SAFE_MODE`:
  - 新しいエントリを一時停止します。
  - 状態が十分にわかっている場合は、リスクを軽減するアクションを許可します。
  - ユーザーに通知します。
  - 再開する前に手動で確認するか、調整が成功する必要があります。
- 可能な場合はクライアントの注文 ID を使用して、ローカルの決定を取引所と関連付けます。
  命令。
- 正常なシャットダウン時:
  - 新しい注文インテントの作成を停止します。
  - 保留中の内部作業を安全に終了またはキャンセルします。
  - 重大な状態を SQLite にフラッシュします。
  - 最終的な実行時の状態をログに記録します。重要な原則:

> システムは障害が決して起こらないことを保証できません。それはそれを保証するはずです
> 失敗後、何が分かっていて何が分からないかを判断し、回避することができます。
> 危険な 2 番目の間違いを犯します。

## WebSocket の方向

マーケット/アカウントの状態を考慮すると、同期には WebSocket を使用することが推奨されます。

推奨される分割:

```text
WebSocket:
  - ticker / mark price
  - kline
  - order update
  - position update
  - execution update

REST:
  - initial snapshot
  - create orders
  - cancel orders
  - close positions
  - periodic reconciliation
  - fallback after WebSocket disconnect/reconnect
```

REST を完全に削除しないでください。 WebSocket はリアルタイム ストリームです。 RESTは残ります
権威ある修正とコマンド パス。

必要な WebSocket の動作:

- ハートビート/ping監視
- バックオフによる自動再接続
- 古いデータの検出
- REST調整によるメッセージギャップ/ドリフトの回復
- 市場/アカウントの状態が古い場合は戦略を一時停止します

## 構成のリロード方向

現在のスクリプトは、初期化中にのみ構成を読み込みます。将来のバージョン
制御された構成のリロードをサポートする必要があります。

正規のターゲット構成構造は、`SPEC.md` で定義されています。将来のエージェント
`SPEC.md` を更新せずに別の構成形状を作成すべきではありません。
理由を説明しています。

推奨される最初の実装:- 手動リロード コマンド。
- 適用する前に完全な構成を検証します。
- 構成の差分を計算してログに記録します。
- 安全なホットリロード可能なフィールドのみを適用します。
- SQLite に設定バージョンを保存します。
- 検証が失敗した場合は、既存の構成を保持します。

ホットリロード可能な可能性のあるフィールド:

- 取引ペアの有効化/無効化
- 注文金額
- EMA期間
- 値の乗数
- 末尾のしきい値
- ブラックリスト
- 監視間隔
- 通知重大度のしきい値

不用意にホットリロードすべきではないフィールド:

- APIキー/シークレット
- 交換タイプ
- アカウントモード
- データベースのパス
- Redis接続
- 安全な明示的なフローが実装されていない限り、活用

考えられるリロードメカニズム:

- CLI/管理コマンド
- ファイル変更ウォッチャー
- Redis パブ/サブ信号

手動リロードから始めます。自動化は検証と安全な動作の後にのみ追加してください
しっかりしています。

## 段階的なリファクタリング計画

各フェーズは、次のフェーズに進む前に独立してテストできる必要があります。

### フェーズ 0: `uv` によるプロジェクトの基盤

目標:

- 取引動作を変更せずに、最新の Python プロジェクトのスケルトンを確立します。

タスク:- `pyproject.toml` を追加します。
- `uv.lock` を生成します。
- `src/bybit_automation/` パッケージ レイアウトに移行します。
- CLI エントリ ポイントを追加します。
- レガシー スクリプトを参照できるようにしておきます。
- ベースライン テスト/lint ツールを追加します。

推奨されるコマンド:

```bash
uv sync
uv run python -m bybit_automation
uv run pytest
```

受け入れ基準:

- `uv sync` は成功します。
- 新しいパッケージがインポートされます。
- no-op/新しいランタイム エントリ ポイントが開始されます。
- レガシー スクリプトは、意図的に移行しない限り変更されません。

### フェーズ 1: 単一プロセスのランタイム、REST ベース

目標:

- を使用しながら、2 つのランタイム プロセスを 1 つの調整されたプロセスにマージします。
  RESTポーリング。

タスク:

- `App` / `BotRuntime` を作成します。
- 統合された設定読み込みを追加します。
- 統合ロガーを追加します。
- 抜粋:
  - `ExchangeClient`
  - `StrategyEngine`
  - `RiskManager`
  - `OrderManager`
  - `PositionManager`
  - `Notifier`
- エントリー戦略とトレーリングリスクロジックの間で 1 つの実行時状態を共有します。

受け入れ基準:

- 1 つのプロセスでエントリー ロジックとリスク ロジックの両方を実行できます。
・戦略とリスクは直接的には相反するものではない。
- すべての交換の副作用は `OrderManager` を経由します。
- デモ モードでは、読み取り専用同期を開始して実行できます。

### フェーズ 2: SQLite の永続化

目標:

- ボットの状態とイベント履歴を保持します。

タスク:- SQLite スキーマと移行またはスキーマ ブートストラップを追加します。
- WAL モードを有効にします。
- ストア注文、注文イベント、ポジションスナップショット、戦略決定、リスクイベント、
  構成バージョンとボットの状態。
- 最高利益や現在の層などの末尾の状態を維持します。

受け入れ基準:

- ボットは SQLite データベースを作成します。
- 重要な決定/出来事が書かれています。
- 再起動しても追跡状態は失われません。
- SQLite の状態を手動で検査できます。

### フェーズ 3: 安全な起動と調整

目標:

- 起動と再起動を安全にします。

タスク:

- 開始時にオープン注文とアクティブなポジションを取得します。
- 交換状態と SQLite 状態を比較します。
- `SAFE_MODE` を実装します。
- 正常なシャットダウンを追加します。

受け入れ基準:

- スタートアップは、新しいエントリの前に常に調整します。
- 矛盾した状態では、新しいエントリが一時停止されます。
- Ctrl+C/SIGTERM は状態を保存し、正常に終了します。

### フェーズ 4: Redis キャッシュと調整

目標:

## フェーズ 2 実装スライス

SQLite 永続化作業の推奨順序:1. ストレージ基盤:
   - `src/bybit_automation/storage/` を追加、
   - シン SQLite 接続/ブートストラップ モジュールを作成します。
   - 設定されたデータベース パスの親ディレクトリを作成します。
   - `[database.sqlite].wal = true` の場合は WAL モードを有効にします。
   - 最初は標準ライブラリ `sqlite3` を使用し続けます。
2. スキーマのブートストラップ:
   - 冪等なスキーマの作成を追加します。
   - 注文、注文イベント、ポジションのスナップショット、戦略のテーブルが含まれます
     決定、リスク イベント、ボットの状態、構成バージョン、シンボルごとの末尾
     状態、
   - タイムスタンプを ISO-8601 UTC テキストまたは別の文書化された一貫した形式で保存します
     形式。
3. リポジトリ層:
   - ランタイム全体を通して生の SQL を公開するのではなく、小さなリポジトリを追加します。
   - 注文イベント、戦略決定、リスクのための追加/読み取りヘルパーから開始します
     イベント、位置スナップショット、および末尾の状態、
   - 複数行の更新には明示的なトランザクションを使用します。
4. ランタイム統合:
   - ランタイムティックごとに戦略決定とリスク決定を保持します。
   - `OrderManager` が返された後も注文結果を保持します。
   - `PositionManager` 同期後に位置スナップショットを保持します。
   - 最高利益や現在の層などの追跡状態を保存および復元します。
5. 構成バージョンの記録:- 正常にロードされた構成コンテンツの安定したハッシュを計算します。
   - ソースパス、正規化されたコンテンツ、ロード時間、およびリロード理由を保存します。
   - ホットリロードはまだ実装しません。成功した起動/ロードのみを記録します。
6. テストと検証:
   - テストでは一時 SQLite データベース ファイルを使用します。
   - WAL モードを確認します。
   - スキーマのブートストラップが冪等であることを確認します。
   - リポジトリへの書き込みが接続を閉じて再度開いても存続することを確認します。
   - すべてのテストをオフラインに保ち、Bybit 認証情報を不要にします。

そうでない場合を除き、フェーズ 2 にリコンシリエーションまたは `SAFE_MODE` 動作を追加しないでください。
永続性を証明するために厳密に必要です。それらはフェーズ 3 に属します。
